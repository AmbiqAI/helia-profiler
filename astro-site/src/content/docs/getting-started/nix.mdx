The repository flake builds one environment from pinned inputs. Two engineers who enter it from the same commit of `flake.lock` get the same Python packages, heliaAOT release, compilers and J-Link software. This page covers entering it, choosing the heliaAOT release, recording what resolved, and what you still provide yourself.

uv, Ruff, ty and pytest remain the Python workflow inside the environment. The flake builds the Python environment from `uv.lock`, so the uv path and the Nix path use the same package versions.

## Enter the environment

Install [Determinate Nix](https://determinate.systems/install/), which enables flakes. With another Nix install, add `--extra-experimental-features 'nix-command flakes'` to each `nix` command below, or enable both features in your Nix configuration.

```bash
git clone https://github.com/AmbiqAI/helia-profiler.git && cd helia-profiler
nix develop
hpx doctor
```

`nix develop .#contrib` adds pre-commit for contributors. `nix run .#verify-isolation` checks that no tool leaks in from your host profile.

## What the flake pins

| Item | Pinned by | Version in this commit |
|---|---|---|
| nixpkgs, Python, CMake, Ninja, uv | `flake.lock` (nixpkgs) | Python 3.12, CMake 4.3, Ninja 1.13, uv 0.11 |
| Python packages | `uv.lock` | for example neuralspotx 0.9.0, ai-edge-litert 2.2.0 |
| heliaAOT | the `helia-aot` flake input, recorded in `flake.lock` | 0.33.0 |
| Arm GNU Toolchain | `flake.lock` (nixpkgs `gcc-arm-embedded`) | 15.2.Rel1 |
| Arm Toolchain for Embedded (ATfE) | `nix/atfe.nix` | 22.1.0 |
| SEGGER J-Link software | `nix/jlink.nix` | 9.62 |
| ns-cmsis-nn (CORE), NSX SDK and modules (including the `nsx-tflite-micro` LiteRT Micro module), heliaRT | `src/helia_profiler/data/compatibility-baseline-v1.json`, plus the neuralSPOT-X registry lock it names | ns-cmsis-nn v7.47.0, heliaRT 2.2.2 and the other refs listed there; LiteRT Micro source helia-rt v2.1.1 (`0e061ff7`) through the neuralSPOT-X 0.9.0 registry |

The last row is not chosen by the flake. hpx fetches those modules at the pinned commits when it builds firmware, through the same baseline on every install path. Selecting a different heliaAOT release does not move any of them.

## Choose the heliaAOT release

The `helia-aot` input selects the heliaAOT source. By default it is the PyPI source distribution of the release in `uv.lock`, so the default environment needs no credentials. The flake accepts a selection only if a runtime record exists for its version under `src/helia_profiler/data/runtimes/helia-aot/`. That is stricter than `hpx`'s own heliaAOT version range, and it is applied at evaluation.

**A recorded release, from PyPI.** Copy the release's `.tar.gz` source URL from its PyPI page:

```bash
nix develop --override-input helia-aot \
  https://files.pythonhosted.org/packages/a5/a7/ea3f4962c304e176435b57ba1384dcc65abb3a280e1036a3843a4e850b6d/helia_aot-0.33.0.tar.gz
```

**A Git revision.** heliaAOT's repository is private, so this needs SSH access to `AmbiqAI/helia-aot`. The revision must be the commit in the matching runtime record (`source.commit`), and a checkout with uncommitted changes is refused:

```bash
nix develop --override-input helia-aot \
  'git+ssh://git@github.com/AmbiqAI/helia-aot?rev=d31bf2226e58e4120eaf8e6da289b5ee91e2e06b'
```

`--override-input` lasts for one command. To keep a selection for a capture, write it into `flake.lock` and commit the result. Pass the same full URL as above, either the PyPI URL or the `git+ssh://…?rev=` URL:

```bash
nix flake lock --override-input helia-aot <PyPI-sdist-URL or git+ssh URL>
```

`flake.lock` records the URL and content hash of a PyPI selection, or the revision and content hash of a Git selection. `nix flake update` returns `helia-aot` to the default in `flake.nix`. To change the default for everyone, follow the steps in the next section.

When the selection is the release in `uv.lock`, the environment uses the locked wheel. Any other recorded release is built from the selected source against the dependency versions in `uv.lock`. If the release declares a dependency that `uv.lock` does not contain, or needs a version outside what `uv.lock` pins, evaluation stops and names the dependency. Nothing is re-resolved.

The flake refuses these selections at evaluation, before anything is built:

| Selection | Why |
|---|---|
| A version with no runtime record | The profiler has no record of that release. |
| A Git revision that is not the commit its runtime record names, or a checkout with uncommitted changes | It is not the recorded release. |
| A release whose dependencies `uv.lock` does not satisfy | The flake builds against the locked versions only. |
| A release whose ns-cmsis-nn requirement is newer than the baseline | See the compatibility table below. |

### Support a new heliaAOT release

A release becomes selectable once the profiler supports it:

1. Add `src/helia_profiler/data/runtimes/helia-aot/<version>.json`, with `source.commit` set to the release commit.
2. Widen the `aot` extra in `pyproject.toml` and run `uv lock`.
3. Update `src/helia_profiler/fixture_closure.txt`.
4. Requalify, and bump the compatibility baseline if the release needs a newer ns-cmsis-nn.
5. If `uv.lock` now locks the new release, set the `helia-aot` input URL in `flake.nix` to its sdist URL from `uv.lock` and run `nix flake lock`. The `helia-aot-default` check fails until the two match.
6. If the baseline's ns-cmsis-nn moved, map the new commit to its release in `nix/compat.nix` (`nsCmsisNnReleases`). Until it is mapped, the environment still builds, but identities reports the baseline as unmapped and the `compat-baseline` check fails.

## Compatibility

Each heliaAOT release needs a minimum ns-cmsis-nn. The flake checks the selected release against the ns-cmsis-nn version in the compatibility baseline. The rules live in `nix/compat.nix`, and `nix flake check` tests them.

| heliaAOT | Minimum ns-cmsis-nn | Baseline in this commit |
|---|---|---|
| 0.33.0 and later, including 1.0 | 7.47.0 | v7.47.0: supported |

Releases older than 0.33.0 have no rule and are refused.

Moving the baseline changes the ns-cmsis-nn that heliaAOT, heliaRT and ExecuTorch builds share. The runtimes that use it are requalified before it moves.

## Record what resolved

```bash
nix run .#identities > identities.json
```

The output is JSON. It records:
- the flake revision and content hash, and the nixpkgs revision. Under `--override-input`, Nix drops the flake revision, so identify a capture by a committed `flake.lock` pin;
- the heliaAOT version, its record commit, the selected input's revision (Git) and content hash, whether the selection was matched by Git commit or by version, and whether it came from the `uv.lock` wheel or the selected source;
- the compatibility baseline refs, including ns-cmsis-nn, its required minimum and whether its commit is mapped;
- the compiler and J-Link versions;
- the versions installed in the Python environment.

Add `--override-input` to report a different selection. Keep the file with any results you capture.

## What Nix cannot provide

- **J-Link licence terms.** The flake downloads the SEGGER J-Link software under SEGGER's terms of use. Using it means accepting them.
- **USB and probe access.** On Linux, install the udev rules for J-Link and Joulescope with `nix run .#install-udev-rules` (see [Linux USB permissions](../install/#5-linux-usb-permissions)). Windows needs WSL2 with `usbipd-win`, and macOS needs no rules. The probe, the board and the Joulescope are physical prerequisites.
- **Credentials.** The default environment and PyPI selections need none. A heliaAOT Git selection needs SSH access to `AmbiqAI/helia-aot`. Any other private repository your configuration names needs the matching access.
- **Network access at build time.** `hpx` fetches NSX modules, including ns-cmsis-nn, at their pinned commits when it first builds firmware. It caches them, so later builds reuse them.

## Caches and outputs

| Location | Contents | Safe cleanup |
|---|---|---|
| `/nix/store` | Everything the flake builds or downloads | `nix store gc` removes only paths nothing references. On a shared machine, agree on it with the other users first. |
| `~/.cache/nix` | Nix fetcher and evaluation caches | Safe to delete; Nix refetches. |
| `$HPX_CACHE_DIR`, else `$XDG_CACHE_HOME/helia-profiler`, else `~/.cache/helia-profiler` | Firmware workspaces, example models and engine downloads | `hpx cache info` shows it. `hpx cache purge` removes the cached firmware workspaces and the NSX module cache. The other subdirectories are re-created on demand and can be deleted by hand. |
| The run's output directory | Firmware, logs and results | Delete it when you no longer need the results. |
