## Goal

Get the complete counter picture of a model rather than the default four.
You will learn how hpx schedules more counters than the hardware holds at
once, what the merged CSV looks like, and which derived ratios to compute.

## Hardware and wiring

An Apollo510 EVB (Cortex-M55 with the Armv8-M PMU and MVE) on its J-Link
USB port. A Cortex-M4 board cannot run this recipe: it exposes the DWT
cycle counter only ([Boards and targets](../../guide/boards/)).

## Software prerequisites

hpx with the `aot` extra (the config uses heliaAOT), the GNU Arm
toolchain, CMake, Ninja and J-Link software.

## Config file

[`examples/quickstart/hpx_full_sweep.yml`](https://github.com/AmbiqAI/helia-profiler/blob/main/examples/quickstart/hpx_full_sweep.yml):

```yaml
model:
  path: kws_model.tflite
  arena_size: 131072
engine:
  type: helia-aot
  config:
    prefix: hpx
    module_name: hpx_model
target:
  board: apollo510_evb
  toolchain: arm-none-eabi-gcc
profiling:
  pmu_counters:
    cpu: all
    memory: all
    mve: all
  per_layer: true
  iterations: 5
  warmup: 2
power:
  enabled: false
output:
  format: csv
  dir: ./results/results_full_sweep
  model_explorer: true
  detailed: true
```

`all` on three groups asks for every counter the SoC's catalogue lists for
that group; the [PMU counters](../../guide/pmu-counters/) page carries the
catalogue per SoC.

## Run

```bash
cd examples/quickstart
hpx profile --config hpx_full_sweep.yml
```

`detailed/profile_<preset>.csv` per firmware pass and
`detailed/profile_<group>.csv` per group, plus `detailed/memory.json`.

## How to read it

- The SoC holds a fixed number of PMU counters at once, so the firmware
  runs the model once per counter preset (`<group>_<index>`, for example
  `cpu_0`, `cpu_1`, `memory_0`) and the host merges the presets by layer
  id. Every row is therefore the same operator measured in several passes;
  `cycles` comes from the pass that carried `ARM_PMU_CPU_CYCLES`
  ([Data capture](../../guide/concepts/capture/)).
- Ratios are more useful than raw counts: `ARM_PMU_L1D_CACHE_REFILL /
  ARM_PMU_L1D_CACHE` is the data-cache miss rate, `ARM_PMU_MVE_INST_RETIRED
  / ARM_PMU_INST_RETIRED` the vector share, `STALL_BACKEND / CPU_CYCLES`
  the fraction of cycles waiting on memory or the pipeline. The
  [PMU counters](../../guide/pmu-counters/#5-read-the-results) page lists
  the derived metrics hpx computes and the ones to compute yourself.
- `overflow` is `True` when a 32-bit counter saturated in any pass; the
  run is then `invalid` for that counter and fewer iterations or fewer
  counters per pass fix it.
- `macs`, `ops` and `cycles_per_mac` join the host-side model analysis to
  the measured row by the operator's original index, so heliaAOT rows
  line up with the model even where the compiler skipped operators.

## Variations

- One group at a time: `pmu_counters: {memory: all}` keeps the run short
  and the passes few.
- Explicit lists: `memory: [ARM_PMU_L1D_CACHE, ARM_PMU_L1D_CACHE_MISS_RD]`
  names counters under the group that owns them; an unsupported name or
  group for the SoC is rejected at preflight.
- heliaRT instead of heliaAOT: the counters are engine-independent; only
  the operator rows differ.
- Overlays: `output.model_explorer: true` writes one overlay per counter
  for [Model Explorer](../model-explorer-overlay/).
