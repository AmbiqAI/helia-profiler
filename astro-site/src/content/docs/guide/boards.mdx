Choose the board and everything the `target` block decides about it: which
counters exist, which clock the core runs at, which probe flashes it, and
what to do when your board is not in the registry.

## Prerequisites

`hpx boards` from [Validate your setup](../../getting-started/validate-your-setup/)
prints the registry for the hpx you installed; the tables here explain its
columns. Nothing on this page needs a board attached until the clock and
probe steps.

The accepted rows are HPX policy in `platform/policy.py`, projected with
helia-platforms facts by `platform/catalog.py`; the

validation backs it, not whether hpx will drive it. `hpx boards` is the
live list for your installed version and wins over this table.

:::caution[Atomiq110 support is experimental]
hpx support for the Atomiq110 SoC and the `atomiq110_fpga_turbo` board is
experimental: best effort, not a release blocker, and outside the
compatibility guarantees for production-silicon targets. The only upstream
realisation is a Cortex-M55 plus Ethos-U85 FPGA carrier with no PSRAM and
no onboard radio; its clock rates, cycle counts, latency, power and energy
describe the FPGA image only. The FPGA exposes the full PMU and MVE
profiling and the Ethos-U NPU through the `ethos_u` engine backend with the
`ethos_npu` counter group; see the
[NPU profiling example](../../examples/atomiq110-npu-profiling/).
:::

`apollo5b_evb` is retained as an SDK-descriptor compatibility spelling, not
a sourced catalog hardware target. See [Platform facts and policy](../concepts/platforms/)
for provenance, exceptions and saved-format compatibility.

## Steps

### 1. Know what the SoC family can capture

hpx models hardware as board over SoC. The board fixes the J-Link device
string, USB ids and pin defaults; the SoC fixes the core, the counters and
the memory layout.

| Family | Cores | Counters | Per-layer detail | MVE group | Power capture |
|---|---|---|---|---|---|
| AP5 (Apollo510, Apollo510B, Apollo5B, Apollo330P, Apollo510 Lite, Atomiq110) | Cortex-M55 | Armv8-M PMU: 8 configurable event counters plus a cycle counter, events across the `cpu`, `memory` and `mve` groups | full | yes | yes |
| AP4 (Apollo4 Plus, Apollo4 Lite) | Cortex-M4 | DWT cycle counter only | cycles only | rejected at preflight | yes |
| AP3 (Apollo3 Plus) | Cortex-M4 | DWT cycle counter only | cycles only | rejected at preflight | yes |

Apollo330P is a Cortex-M55 part in the AP5 family despite the 3 in its
name. On an AP4 or AP3 board a `memory` or `mve` selection is rejected at
preflight with the groups that board does expose
(`platform/counters.py`, `validate_group_selection`); drop those keys to
capture cycles only. The counter groups themselves are on
[PMU counters](../pmu-counters/).

Fitted PSRAM comes from the catalog: the plain
Apollo3 Plus, Apollo330P, Apollo510 Lite and Apollo4 EVBs have none; Cygnus
has 8 MiB, and Apollo510/510B have 64 MiB. HPX separately decides whether the
`usb_cdc` transport is available (`SocDef.has_usb`; Apollo3P and Atomiq110
have no compatible `nsx-ambiq-usb` module, so `usb_cdc` is rejected at
preflight there).

Each family also selects the AmbiqSuite SDK tier and the neuralSPOT-X
modules the firmware build pulls in (`nsx-ambiqsuite-r5`, `nsx-ambiq-hal-r5`,
`nsx-ambiq-bsp-r5` for AP5; `-r4` and `-r3` for the others). This follows
from `target.board` and needs no configuration.

### 2. CPU clock

`target.clock.cpu` selects the core frequency by the SoC's named tier
(`lp` or `hp` on the Apollo parts; `atomiq110_fpga_turbo` exposes `lp`
only, a single fixed FPGA clock). The tiers and their frequencies are
projected from catalog operating points by `platform/catalog.py`; hpx validates
the name against them and maps it onto the matching neuralSPOT-X
performance mode in the generated firmware. Unset, the board runs at its
lowest-power tier. `run_metadata.json` records the resolved tier and
frequency for every run, which is the number to quote.

```yaml
target:
  board: apollo510_evb
  clock:
    cpu: hp
```

Cycle counts depend on the clock only through memory timing; energy and
latency depend on it directly, so record it with every comparison.

### 3. Pin the probe

With one probe attached nothing needs setting. With several,
`hpx probes match --board <name>` shows the pick, and `target.jlink_serial`
(or `--jlink-serial`) pins it. hpx passes the board's J-Link device string
itself; the values are in the registry (`AP510NFA-CBR` for `apollo510_evb`,
`AMA3B2KK-KBR` for `apollo3p_evb`, and so on) and never need typing.

### 4. Add a custom board or SoC

A board that behaves like a built-in EVB is a `target.custom_boards` entry
that inherits from it:

```yaml
target:
  board: apollo510_lab
  custom_boards:
    apollo510_lab:
      based_on: apollo510_evb
      channel: dev
      default_sync_gpio_pin: 27
```

A genuinely new SoC and board pair declares the SoC first:

```yaml
target:
  board: apollo510_custom_board
  custom_socs:
    apollo510_custom:
      based_on: apollo510
      jlink_device: AP510-CUSTOM
      rtt_scan_ranges:
        - [0x21000000, 0x100000]
  custom_boards:
    apollo510_custom_board:
      soc: apollo510_custom
      channel: dev
      starter_profile_board: apollo510_evb
```

The facts a custom entry carries are the registry's: board name and SoC
family, J-Link device string, memory layout, the application flash load
address, and the default sync GPIO pin (most built-in EVBs register their
own; `10` is only the fallback for a board without one).
`starter_profile_board` reuses a built-in board's neuralSPOT-X starter
profile while keeping the custom board's own id, channel, pin and SoC facts.
Unrecognised keys are rejected with the list of supported keys and a
close-match suggestion.

`custom_socs.<name>.based_on` also inherits controls that cannot be set as
custom keys: USB availability, the host SWO reference-clock setting, the shared
SRAM power enum, radio-shutdown eligibility and the known CPU data-cache fact.
This applies through custom chains, whether their base is builtin or comes
from a catalog overlay. An SDK part/header override must support the radio
shutdown API before HPX emits its call; changing the route does not grant an
ancestor without radio-shutdown eligibility that capability. A supported
descendant can recover eligibility after an unsupported intermediate route.
Explicit family, core and MVE settings remain effective, but a known inherited
cache fact takes precedence over the generic family fallback. An unknown cache
fact stays unknown and uses the existing fallback.

These inherited inputs do not make a derivative a qualified builtin. It keeps
custom provenance and does not borrow builtin linker windows, strict compiled
receipts or fixed-fixture admission. Self-contained definitions without
`based_on` retain their defaults.

Pins are plain integer pad numbers; booleans are rejected because a pin
here is driven for the whole measured window. `0` on
`default_state_gpio_pin` or `default_go_gpio_pin` disables that wire and
degrades the 3-wire handshake to the 1-wire gate; `0` on
`ble_reset_gpio_pin` is rejected as ambiguous (omit it, or write `null`,
on a board without an onboard radio). `ble_reset_gpio_pin` names the GPIO
wired to a Blue board's Cooper BLE controller reset line, held low during
power captures so an idling radio stays out of the measurement.

#### Reuse a catalog overlay

Use `target.platform_overlay` to read one explicit local
[helia-platforms overlay](https://github.com/AmbiqAI/helia-platforms).
For example, save this as `lab-platform.yaml`:

```yaml
schema_version: 1
boards:
  lab:
    based_on: apollo510_evb
```

Then select it in the profiling config:

```yaml
target:
  board: lab
  platform_overlay: lab-platform.yaml
  custom_boards:
    lab:
      based_on: lab
      default_sync_gpio_pin: 27
```

The overlay supplies catalog facts. The optional `custom_boards` entry above
sets HPX measurement wiring with the existing custom-declaration syntax.
HPX retains an exact supported board policy for the requested name; otherwise
it selects the nearest supported board policy from catalog lineage. The board
policy supplies the neuralSPOT-X starter profile; SoC policy resolves independently. Catalog entries
cannot replace builtins; HPX custom declarations retain their existing
precedence. Self-contained HPX definitions need no catalog overlay.

Relative overlay paths resolve against the working directory when configuration
is loaded, including `Session.from_yaml`, `Session.from_dict` and `load_config`;
they are not relative to the config file. `~` expands and the resolved absolute
locator is retained. Programmatic callers pass the same field through these
loaders. There is no new CLI flag, plugin discovery or environment search.

Only the selected target and bases referenced by HPX custom declarations are
projected. A native target needs supported board and SoC policy lineages that
select the same NSX target. HPX currently requires the inherited core identity,
non-PSRAM address geometry, trace clock and CPU frequencies exposed by HPX
policy, and whole-KiB memory capacities;
PSRAM must retain an address supported by the inherited HPX placement policy
where one is known. Only one populated, directly core-reachable PSRAM region
can be represented; an unknown address stays unknown. Unsupported projections
raise `ConfigError`; use an explicit HPX custom declaration where appropriate.

Every projected overlay target is custom, including compositions of builtin
leaves and selecting a builtin through an explicit overlay. It does not inherit
builtin linker-source qualification, strict compiled receipts or fixed-fixture
admission. heliaAOT still needs an explicit supported
`engine.config.platform_name` for a new board name; this does not establish
physical equivalence or automatically forward the overlay to the compiler.

Resolution freezes the facts and file digest. Saved `FrozenRun` readers use
retained facts even if the file changes or disappears. Fresh execution from the
saved plan checks the file binding and refuses changed or missing input before
resolving it again. Merely adding support for `platform_overlay` does not change
the settings or intent of a plan that omits it. Resolved capability corrections
can still change an intent; see [retained platform input](../concepts/platforms/#retained-platform-input).

#### Application flash load address

`app_flash_load_addr` is the first flash address above the part's
bootloader-reserved region, where neuralSPOT-X programs application
images. hpx uses it only as a fallback for flashing the dedicated
power-measurement binary when the generated `flash_cmds.jlink` recipe is
missing; when the recipe exists it wins, and a disagreement between the two
logs `DECLARED FLASH ADDRESS IGNORED` naming both. Investigate that warning
rather than filter it: it means the build and the declaration disagree
about which part this is.

- `based_on: <soc>` inherits the address with everything else; the usual
  case.
- Set it explicitly when the bootloader reservation differs from the part
  you based on.
- A custom SoC with neither `based_on` nor `app_flash_load_addr` has no
  address, and hpx refuses the fallback flash rather than guess one from
  `family`, which records a core tier, not a memory map. Writing
  `app_flash_load_addr: null` explicitly is the same refusal and overrides
  inheritance.

The programmatic API has no `based_on`: a `SocDef` you construct for
`build_platform_registry(socs=...)` carries the address as a field, or
`soc.capabilities.memory.app_flash_load_addr` is `None`. The
[platform API reference](../../reference/api/)
documents `get_soc`, `SocDef` and `build_platform_registry`.

## Expected output

`run_metadata.json` records the resolved board, SoC, clock tier and probe
serial for every run. `hpx boards` prints the registry your installed hpx
carries; if a board is missing there, a custom entry is the way to add it.
