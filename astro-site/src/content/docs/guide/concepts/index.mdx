## Purpose

This section is for contributors and for agents that change hpx rather
than run it. It names the packages, says what each one owns and hands on,
and points at the module behind every block, so a change can be placed
before it is written. Users who only run `hpx profile` need the
[User guide](../../guide/), not this.

The same structure as a list, for readers of the Markdown rendition:

- Entry points: `cli` (Typer commands), `api` (`profile()`), `session` (notebooks)
- Configuration: `config` (`ProfileConfig`, frozen), `vocab` (shared enums), `placement` (policy)
- Pipeline: `pipeline` (`Stage`, `PipelineContext`, `PipelineRunner`), `profiler` (default stage list), `stages` (one module each)
- Engines: `base` (adapter protocol), `tflm`, `helia_rt`, `helia_aot`, `executorch`
- Firmware: `templates` (Jinja2), `project` (NSX files), `build` (nsx configure, build), `fingerprint`
- Dependencies: `compatibility` (baseline), `dependencies` (workspaces, locks), `nsx` (subprocess), `sync`
- Platform: `soc`, `board`, `counters` (PMU registry), `memory_map`, `custom` (overlays)
- Target: `lifecycle` (reset policy), `probe` (J-Link)
- Transport: `rtt`, `usb_cdc`, `uart`, `swo`, `protocol` (line loop)
- Capture: `parser` (stream to `PmuResult`), `readiness`, `power_terminal`
- Power: `joulescope`, `ina228_driver`, `ondevice_driver`, `sync` (gate contract)
- Results: `results` (typed models), `report` (writers), `evaluation` (validity, compare), `modelcost` (MACs, attribution)
- Host and wire: `hostenv` (doctor, toolchains), `diagnostics` (support bundle), `validation` (`hpx validate`), `wire` (protocol spec)

## The blocks

hpx is a profiler, not a build system, an SDK exporter or an application
framework. It generates a disposable firmware app for one model and one
engine, builds it with NSX, flashes it, captures what the firmware prints,
and writes a result bundle. Four rules shape every package:

| Rule | What it means in code | Where it is enforced |
|---|---|---|
| Immutable configuration | `ProfileConfig` is resolved once from the CLI and YAML, then frozen; every stage reads the same object and none mutates it | `config/__init__.py` (frozen pydantic models with `extra="forbid"`) |
| One engine per run | the engine is explicit; comparing engines means two runs and `hpx compare` | `engines/__init__.py` (`get_adapter` takes one `EngineType`) |
| Typed stage boundaries | stages exchange dataclasses from `results/`, never dicts; the one dynamic field is `LayerResult.counters` because counter names come from the SoC | `results/models.py`, `results/artifacts.py` |
| Subprocess isolation | GCC, CMake, J-Link and the heliaAOT compiler run through `subprocess.run()` with argument lists, never a shell | `deps/nsx.py`, `target/probe/jlink.py`, `engines/helia_aot/compile.py` |

### Two objects flow through everything

`ProfileConfig` is the read-only input. `PipelineContext` is the mutable
state bag the stages fill: each stage sets the fields it owns and reads the
fields earlier stages set, through narrowing accessors that raise
`PipelineError` naming the producing stage when it has not run. The
[Pipeline](pipeline/) page lists both.

### Errors are typed

Every failure is a subclass of `HpxError` carrying an optional `hint` that
the CLI prints under the message. The subclass says which package failed:

| Error | Raised by | Meaning |
|---|---|---|
| `PipelineError` | `pipeline.py` | a stage product was read before its stage ran |
| `ConfigError` | `config/` | bad YAML, unknown key, missing field |
| `PlatformError` | `platform/` | unknown board or SoC |
| `EngineError` | `engines/` | adapter failure |
| `FirmwareError` | `firmware/` | template rendering failure |
| `BuildError` | `deps/`, `firmware/build.py` | NSX configure or build failure; `NetworkError` and `DependencyError` (`VersionError`, `LockError`) narrow it |
| `CaptureError` | `capture/`, `transport/`, `target/probe/` | transport, protocol or firmware-reported failure; `DeterministicCaptureError` narrows it for refusals a retry cannot change, such as a missing image or an unknown load address on the flash path |
| `PowerError` | `power/` | driver failure |
| `ReportError` | `report/` | output failure; `ValidationBundleError` narrows it for `hpx validate` bundles |

The list is `src/helia_profiler/errors.py`; the CLI maps every `HpxError`
to a non-zero exit and the codes in the run's `issues` are a separate
vocabulary, documented on the [issue codes](../../reference/issue-codes/)
page.
